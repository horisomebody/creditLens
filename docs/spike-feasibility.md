> 실행 노트북: `ml/notebooks/spike_feasibility.ipynb` (2026-09-17 실행, 에러 없이 전 구간 완주)
> 여기서 쓴 전처리·하이퍼파라미터는 가안이며 최종 방침이 아니다. 전처리는 Phase 2, 모델 튜닝은 Phase 3, SHAP 사유 코드 설계는 Phase 4에서 별도로 정한다.

## 결론

**파이프라인은 끝까지 막힘없이 돈다.** 데이터 로드 → 최소 전처리 → 로지스틱 회귀 베이스라인 → XGBoost → SHAP →
임계값별 승인율/부실률 표까지 전체 실행 시간 약 1초(15만 행 기준, SHAP 포함). 계획대로 완주 가능하다고 판단한다.

단, 아래 "예상 밖 발견" 항목은 Phase 3에서 반드시 다시 짚어야 한다.

## 2. 최소 전처리 (가안)

- 연체 변수 3개의 96/98 코드값 → 결측 처리 후 중앙값 대체
- `MonthlyIncome`, `NumberOfDependents` → 중앙값 대체
- 전체 피처를 하한 0.5% / 상한 99.5% 분위수로 클리핑(winsorize)
- 처리 후 결측 0건, 에러 없음

## 3. 모델 비교 (홀드아웃 20%, 층화 분할)

| 모델 | AUC |
|---|---|
| 로지스틱 회귀 (`class_weight="balanced"`) | 0.8597 |
| XGBoost (기본 하이퍼파라미터 + `scale_pos_weight=13.96`) | 0.8490 |

### 예상 밖 발견

**튜닝 없는 XGBoost가 로지스틱 회귀 베이스라인보다 AUC가 낮다(-0.0106).**
이 데이터셋은 변수가 10개뿐이고 관계가 비교적 단순해서 로지스틱 회귀만으로도 강력한 베이스라인이 나오는 것으로 보인다.
`scale_pos_weight`가 트리 분기 자체에 영향을 줘 랭킹(AUC)을 오히려 낮췄을 가능성도 있다.
→ Phase 3에서 하이퍼파라미터 탐색, `scale_pos_weight` 유무 비교, 확률 보정을 반드시 확인해야 한다.

**후속 결정 (2026-09-17)**: Phase 3에서 XGBoost를 튜닝한 뒤 로지스틱 회귀 베이스라인과 AUC를 비교해 최종 모델을 결정하기로 함.
`CLAUDE.md`, `docs/project-plan.md` Phase 3에 반영.

## 7-1. 후속 검증: 튜닝 후 XGBoost vs 로지스틱 회귀

> 실행 노트북: `ml/notebooks/spike_tuning_comparison.ipynb` (2026-09-17 실행, 전체 20.7초)

두 모델 모두 5-fold CV로 하이퍼파라미터를 탐색한 뒤 동일한 홀드아웃(20%)에서 비교했다.
전처리는 5절과 동일한 가안(중앙값 대체 + winsorize)을 그대로 사용했다.

| 모델 | 최적 파라미터 | CV AUC | 홀드아웃 AUC |
|---|---|---|---|
| 로지스틱 회귀 | `C=0.001`, `class_weight=balanced` | 0.8542 | 0.8598 |
| XGBoost | `max_depth=5`, `n_estimators=259`, `learning_rate=0.045`, `scale_pos_weight=1`, 기타 탐색값 | 0.8647 | 0.8691 |

**튜닝된 XGBoost가 홀드아웃 AUC 기준 로지스틱 회귀보다 +0.0094 높다.** 방향은 뒤집혔다(이전 스파이크에서는 미튜닝 XGBoost가 더 낮았음).
다만 폭은 크지 않다 — 관례적 기준(+0.01~0.02 이상을 "실질적"으로 보는 기준)에 딱 못 미치는 수준이라, "확실히 우월하다"기보다는
**작지만 일관된 우위** 정도로 보는 게 정확하다.

주목할 점: 탐색 결과 최적 `scale_pos_weight=1`(미적용)이 선택됐다. 이전 스파이크에서 세운 가설
("`scale_pos_weight`가 랭킹을 오히려 낮췄을 가능성")이 맞았던 것으로 보인다.

### 판단

- XGBoost를 최종 채택하는 근거: AUC가 일관되게(CV·홀드아웃 모두) 앞서고, SHAP 기반 사유 코드라는 프로젝트의 핵심 설명 가능성 스토리와도 맞는다.
- 로지스틱 회귀를 최종 채택하는 근거: AUC 차이가 크지 않고, 계수 해석이 SHAP보다 더 단순·직관적이며 금융권에서 스코어카드로 익숙한 방식이다.
- 이 스파이크는 판단 근거만 제공한다. 최종 모델 결정은 사용자 몫이며, `CLAUDE.md`·`docs/project-plan.md`에 반영해야 한다.

## 7-2. 후속 검증: 고위험 상위 5% 포착 성능

> 실행 노트북: `ml/notebooks/spike_tuning_comparison.ipynb` 6절 (동일 홀드아웃, 튜닝된 두 모델 기준)

전체 순위(AUC) 대신, 실무적으로 더 자주 쓰는 질문 — "예측 부실 확률이 가장 높은 상위 5%를 골라내면 얼마나 정확한가" —
로도 비교했다.

| 지표 | 로지스틱 회귀 (튜닝) | XGBoost (튜닝) |
|---|---|---|
| 상위 5% 내 실제 부실 비율(정밀도) | 47.47% | 48.00% |
| 전체 부실자 중 상위 5%가 잡아낸 비율(포착률) | 35.51% | 35.91% |
| lift(전체 평균 6.68% 대비 배수) | 7.10배 | 7.18배 |

**상위 5% 기준으로는 두 모델이 사실상 동률이다** (정밀도 차이 0.5%p, 포착률 차이 0.4%p). 전체 AUC에서 봤던 작은 우위(+0.0094)조차
"가장 위험한 상위권을 골라내는" 실무 시나리오에서는 거의 사라진다. 두 모델 모두 무작위 대비 약 7배 진하게 부실자를 상위 5%에 몰아넣는다는 점은 동일하다.

## 7-3. 후속 검증: 피처 엔지니어링을 추가하면 격차가 벌어지는가

> 실행 노트북: `ml/notebooks/spike_feature_engineering.ipynb` (2026-09-17 실행, 24.9초)

`docs/project-plan.md` Phase 2 파생 변수 후보 중 4개를 추가해 같은 방식(5-fold CV 튜닝)으로 재비교했다.

- `IncomeMissingFlag`: 원본 `MonthlyIncome` 결측 여부
- `TotalPastDue`: 연체 변수 3개 합계
- `WorstDelinquencyStage`: 도달한 최악 연체 단계(0~3)
- `IncomePerDependent`: `MonthlyIncome / (NumberOfDependents + 1)`

| 모델 | AUC (원본 변수) | AUC (피처엔지니어링 후) | 개선폭 |
|---|---|---|---|
| 로지스틱 회귀 | 0.8598 | 0.8619 | +0.0021 |
| XGBoost | 0.8691 | 0.8693 | +0.0002 |

**격차는 벌어지지 않고 오히려 좁혀졌다** (+0.0093 → +0.0074). 로지스틱 회귀가 파생 변수로 더 많이 개선된 반면
XGBoost는 거의 그대로다. 상위 5% 포착 성능은 방향이 엇갈렸다 — 로지스틱 회귀는 소폭 하락(정밀도 -0.14%p),
XGBoost는 소폭 상승(정밀도 +0.33%p) — 하지만 둘 다 노이즈 수준이라 유의미한 역전으로 보기는 어렵다.

이유를 뒷받침하는 근거: XGBoost 피처 중요도에서 `WorstDelinquencyStage`가 전체 14개 변수 중 **1위**(0.367),
`TotalPastDue`가 3위(0.139)로 나왔다. 즉 이 파생 변수들이 담은 정보를 XGBoost는 원본 변수(연체 3개)의 분기 조합만으로도
**이미 상당 부분 스스로 찾아내고 있었고**, 명시적으로 파생 변수를 만들어준 것은 그 정보를 미리 정리해 로지스틱 회귀 같은
선형 모델이 더 쉽게 쓸 수 있게 해준 효과가 컸다는 뜻이다. `IncomeMissingFlag`, `IncomePerDependent`는 두 모델 모두에게
중요도가 낮았다(14개 중 11위, 13위) — 새 정보량이 적은 파생 변수였던 것으로 보인다.

**결론**: 이 데이터셋에서는 피처 엔지니어링을 더해도 XGBoost 우위가 뚜렷해지지 않는다는 근거가 하나 더 쌓였다.
트리 모델이 원본 변수만으로도 비선형·상호작용을 상당 부분 스스로 찾아낼 수 있는 단순한 데이터 구조이기 때문으로 보인다.
