# CreditLens 프로젝트 계획

> 항목 표기: **[확정]** 사용자가 결정한 사항 / **[제안]** 논의 중 나온 미확정 제안 / **[미결정]** 진행 중 정해야 할 사항

## 0. 변경 이력

- **2026-09-17**: 데이터셋 전략을 GMC 단독 → GMC(비교군) + Home Credit Default Risk(주 데이터셋)로 변경. 사용자 승인.
  프로젝트 목표를 "데이터 복잡도에 따른 선형/비선형 모델 성능 격차와 SHAP 설명력"을 다루는 연구 질문으로 재정의.
  상세 사유는 1절·2절 참고. `CLAUDE.md`의 확정 항목도 함께 갱신됨.

## 1. 목표

설명 가능한 개인 대출 연체 위험 예측 시스템을 만든다. 예측 결과마다 고객에게 제시 가능한 사유를 함께 제공하고,
배치 파이프라인으로 정기 재스코어링하는 운영 형태까지 구현한다.

프로젝트 중심에는 다음 연구 질문이 있다:

> **데이터의 복잡도(변수 수, 테이블 구조)에 따라 선형 모델(로지스틱 회귀)과 비선형 모델(XGBoost)의 성능 격차가
> 어떻게 달라지는가? 그리고 비선형 모델을 선택해야 하는 조건에서, SHAP 기반 설명 체계가 스코어카드에 준하는
> 설명력을 확보할 수 있는가?**

이 질문이 생긴 배경: 단순 정형 데이터(GMC, 변수 10개)로 스파이크를 수행한 결과, 튜닝된 XGBoost가 로지스틱 회귀보다
AUC +0.0094, 상위 5% 고위험군 포착에서도 근소한 우위만 보였고, 피처 엔지니어링을 더해도 격차가 좁혀졌다
(`docs/spike-feasibility.md`). 즉 "성능 이득이 없으면 설명이 어려워지는 비용을 감수하고 XGBoost를 쓸 이유가 없다"는
문제 제기가 실증적으로 뒷받침됐다. 이를 GMC 하나만으로 결론짓지 않고, 다중 테이블·고결측·범주형 변수를 가진
더 복잡한 데이터(Home Credit Default Risk)에서는 격차가 실제로 벌어지는지 비교해 답한다.

결과가 어느 쪽으로 나오든(격차가 벌어지든, 안 벌어지든) 실증적 결론이 되고, 두 경우 모두 포트폴리오에서
"왜 이 모델과 설명 방식을 택했는가"에 근거를 가진 답을 준다.

## 2. 데이터 [확정]

두 데이터셋을 함께 쓴다. GMC는 이미 검증이 끝난 비교군, Home Credit Default Risk는 이번에 추가하는 주 데이터셋이다.

### 2-1. Give Me Some Credit — 비교군 (GMC)

단일 테이블, 대출자 1명 = 1행. 학습 파일 약 15만 건. 전부 수치형 변수 10개.

| 컬럼 | 의미 |
|---|---|
| SeriousDlqin2yrs | 타깃. 향후 2년 내 90일 이상 연체 여부 |
| RevolvingUtilizationOfUnsecuredLines | 무담보 리볼빙 한도 사용률 |
| age | 나이 |
| NumberOfTime30-59DaysPastDueNotWorse | 30~59일 연체 횟수 |
| DebtRatio | 월 부채 상환액 / 월소득 |
| MonthlyIncome | 월소득 |
| NumberOfOpenCreditLinesAndLoans | 보유 대출·신용한도 건수 |
| NumberOfTimes90DaysLate | 90일 이상 연체 횟수 |
| NumberRealEstateLoansOrLines | 부동산 담보 대출 건수 |
| NumberOfTime60-89DaysPastDueNotWorse | 60~89일 연체 횟수 |
| NumberOfDependents | 부양가족 수 |

**이 데이터를 비교군으로 쓰는 이유**

- 모든 변수의 의미가 명확해 SHAP 결과를 사유 코드로 옮기기 쉽다.
- 타깃 정의(90일 이상 연체)가 금융권 부도 정의와 가깝다.
- 민감 변수가 적다(나이 정도).
- 변수 10개짜리 "단순한 데이터"의 기준선 역할 — 연구 질문의 한쪽 끝(낮은 복잡도)을 담당한다.

**알려진 한계 (README에 명시)**

- 2011년 대회 데이터이며 한국 시장 데이터가 아니다.
- 변수가 10개라 사유 코드 종류가 제한적이고, 연체 변수 3개가 겹쳐 비슷한 사유가 반복될 수 있다.
- 단일 테이블이라 다중 테이블 피처 엔지니어링은 보여주기 어렵다 → 이 한계를 Home Credit으로 보완한다.
- 날짜 정보가 없어 시간 순 검증과 실제 드리프트 관측이 불가능하다.
- 승인된 대출자만 포함되어 있을 가능성(선택 편향)이 있다.
- `cs-test.csv`에는 `SeriousDlqin2yrs` 컬럼은 있으나 값이 전부 결측(대회 채점용, 비공개).

**검증 상태**: 스파이크로 실측 검증 완료 (2026-09-17, `docs/spike-feasibility.md`). 홀드아웃 AUC 로지스틱 회귀
0.8598 vs XGBoost 0.8691(+0.0094), 상위 5% 포착 정밀도 47.47% vs 48.00%, 포착률 35.51% vs 35.91%, lift 7.10배 vs 7.18배.
피처 엔지니어링 후 격차는 오히려 좁혀짐(+0.0093 → +0.0074).

### 2-2. Home Credit Default Risk — 주 데이터셋 (신규, 2026-09-17 추가)

Kaggle 2018년 대회. 다중 테이블 구조로, 주 테이블(`application_train/test`)에 대출자별 특성이 있고
과거 신용 이력·이전 대출 이력이 별도 테이블에 나뉘어 있어 조인·집계가 필요하다.

| 테이블 | 내용 (공개 자료 기준) |
|---|---|
| `application_train/test` | 대출 신청 시점 신청자 정보, 타깃(`TARGET`) 포함 |
| `bureau` | 다른 금융기관에 보고된 과거/현재 신용 정보 |
| `bureau_balance` | `bureau`의 월별 잔액 이력 |
| `previous_application` | Home Credit 내 과거 대출 신청 이력 |
| `POS_CASH_balance` | 과거 POS/현금 대출의 월별 잔액 |
| `credit_card_balance` | 과거 신용카드 월별 잔액 |
| `installments_payments` | 과거 대출 상환 이력 |

데이터는 이미 받아 `data/raw_home_credit/`에 배치됨(2026-09-17, 약 2.5GB). 정확한 행 수·컬럼 수·결측률·타깃 비율은
Phase 5 EDA에서 실측 검증한다(GMC와 동일한 방식).

**주 데이터셋으로 추가하는 이유**

- 연구 질문의 다른 한쪽 끝(높은 복잡도)을 담당 — 다중 테이블, 범주형 변수, 높은 결측률을 가진 데이터에서
  비선형 모델의 성능 이점이 실제로 커지는지 확인할 수 있다.
- 다중 테이블 조인·대규모 피처 엔지니어링·결측/범주형 처리라는, GMC만으로는 보여줄 수 없었던 작업량과 역량을
  포트폴리오에 담을 수 있다.

**알려진 한계 (공개 자료 기준, GMC와 대조됨)**

- 다중 테이블 구조 — 조인 키·집계 로직 설계가 필요하다.
- 결측률이 높은 컬럼이 다수 존재한다.
- 범주형 변수가 다수 존재한다(GMC는 전부 수치형이었음) — 인코딩 전략을 새로 정해야 한다.
- 일부 변수(`EXT_SOURCE_1/2/3` 등)는 정의가 공개되지 않은 블랙박스성 신용 점수다 — SHAP으로 기여도는 보여줄 수 있어도
  "왜 이 값이 높은가"의 근본 설명은 어렵다. 이 한계 자체가 연구 질문("SHAP이 스코어카드 수준 설명력을 확보하는가")의 일부다.
- 타깃 정의가 GMC와 다르다(자체 부도 정의) — 두 데이터셋 결과를 절대 비교할 때 이 차이를 감안해야 한다.
- 데이터 용량이 GMC보다 훨씬 크다(약 2.5GB) — 원천 파일은 저장소에 커밋하지 않는다.

### 검토 후 채택하지 않은 대안

- Home Credit Credit Risk Model Stability (2024): 시간 정보가 있으나 변수 익명화로 설명이 어렵고 규모가 크다. 여전히 미채택.
- ~~Home Credit Default Risk (2018)~~: 과거에는 "블랙박스 변수, 비공개 타깃 정의, 민감 변수 다수로 설명 가능성 불리"라는
  이유로 기각했었다. 2026-09-17 재검토: 그 우려 자체(설명 가능성이 떨어지는 조건에서 SHAP이 얼마나 버티는가)를
  검증 대상으로 삼기로 하면서 채택으로 전환. GMC를 버리지 않고 비교군으로 유지하는 것이 이 우려를 상쇄하는 장치다 —
  최종 프로덕션 설명 방식이 Home Credit에서 잘 작동하지 않으면 GMC 쪽 결과로 대체할 수 있다.

## 3. 단계별 계획

기간은 대략적 배분이며 학기 일정에 맞춰 조정한다. 흐름은 **GMC 파이프라인 완성 → Home Credit 확장 → 두 데이터셋 비교 분석**이다.
전체 48주 배정, 1년(52주) 중 여유 4주(기존 계획 대비 축소됨 — 3절 하단 참고).

### Phase 0. 프로젝트 골격 및 환경 구성 (2주)

- 모노레포: `ml/`(Python), `backend/`(Spring), `infra/`, `docs/` (프론트엔드는 채택 시 추가)
- Docker Compose 로컬 실행 환경, GitHub Actions 기본 빌드
- 데이터 다운로드 안내 또는 스크립트 (원천 CSV는 `.gitignore`)
- **완료 기준**: 로컬에서 빈 서비스가 뜨고 CI가 통과한다

### Phase 1. GMC 데이터 탐색·품질 점검 (3주)

점검 체크리스트:
- [ ] 행 수, 타깃 비율
- [ ] 컬럼별 결측률 (`MonthlyIncome`, `NumberOfDependents`)
- [ ] 연체 변수의 96/98 코드값 분포와 의미 추정
- [ ] `RevolvingUtilization` 1 초과 값 분포
- [ ] 소득 결측·0일 때 `DebtRatio` 분포
- [ ] `age` 이상값(0 등)
- [ ] 중복 행
- [ ] 변수 간 상관(특히 연체 변수 3개)
- [ ] 변수별 타깃 비율 추이

스파이크(`ml/notebooks/spike_feasibility.ipynb`)로 위 항목의 실제 수치는 이미 확보돼 있다. 이 Phase는 그 결과를
정식 EDA 노트북·보고서 형태로 정리하는 단계다.

- **완료 기준**: EDA 노트북, 데이터 품질 보고서, 이상값 처리 방침 문서

### Phase 2. GMC 전처리·피처 (4주)

- 결측 처리 방침(결측 플래그 포함 여부)
- 코드값·이상값 처리
- 파생 변수 후보: 연체 총합·최악 연체 단계, 소득 결측 여부, 1인당 소득 등
  (스파이크에서 우선 검증함 — `ml/notebooks/spike_feature_engineering.ipynb`. `WorstDelinquencyStage`가
  XGBoost 피처 중요도 1위로 나왔으나 로지스틱-XGBoost 격차는 오히려 좁혔다)
- **학습과 스코어링이 같은 전처리 로직을 쓰도록 단일화**
- **완료 기준**: 원천 행 → 피처 벡터 변환이 재현 가능하고 테스트가 있다

### Phase 3. GMC 모델 비교 — 로지스틱 회귀 vs XGBoost (5주)

- 층화 분할(학습/검증/홀드아웃)
- 교차 검증, 하이퍼파라미터 탐색, 불균형 처리 비교(`scale_pos_weight` 유무 포함 — 스파이크에서 랭킹을 오히려 낮추는 것으로 나왔으므로 확인 필요)
- 로지스틱 회귀 베이스라인과 튜닝된 XGBoost의 AUC·상위 위험군 포착 성능을 비교해 GMC 트랙의 최종 모델을 결정한다
  (스파이크 결과: AUC 차이 +0.0094, 상위 5% 정밀도 차이 0.5%p — 정식 CV·KS까지 포함해 재확인 필요.
  `docs/spike-feasibility.md` 참고)
- 평가: AUC, KS, 구간별 연체율
- 모델 아티팩트와 메타데이터(학습일, 파라미터, 성능) 저장
- **완료 기준**: 모델 파일, 성능 보고서(로지스틱 회귀 대비 비교 포함), GMC 트랙 최종 모델 선정 근거

### Phase 4. GMC 설명 체계 — SHAP 또는 스코어카드 사유 코드 (5주)

- Phase 3 결과에 따라 분기: XGBoost가 최종이면 SHAP 기여도 기반, 로지스틱 회귀가 최종이면 계수·WoE 기반으로 사유 코드 설계
- 개별 대출자 기여도 계산
- 위험을 높인 상위 변수 → 사유 코드 매핑 테이블(코드, 고객용 문구, 내부 설명)
- 상관된 연체 변수 3개의 사유 중복 처리 규칙
- 고객에게 노출하지 않을 사유 정책(`age` 등)
- **완료 기준**: 대출자별 상위 N개 사유 코드 생성, 매핑 규칙 문서

### Phase 5. Home Credit 데이터 탐색·전처리·피처 — 다중 테이블 (6주)

- 각 보조 테이블(`bureau`, `previous_application`, `POS_CASH_balance`, `credit_card_balance`, `installments_payments` 등)의
  구조·결측률·타깃 관계를 우선 GMC와 동일한 방식으로 점검
- 대출자 단위로 집계하는 조인·피처 엔지니어링 설계(예: 대출자별 과거 연체 이력 요약, 이전 신청 승인율 등)
- 범주형 변수 인코딩 전략 결정
- 결측 처리 방침(컬럼별 결측률 편차가 커서 GMC보다 세밀한 기준 필요)
- **학습과 스코어링이 같은 전처리 로직을 쓰도록 단일화** (GMC와 동일 원칙)
- **완료 기준**: EDA 노트북·데이터 품질 보고서, 원천 다중 테이블 → 단일 피처 벡터 변환이 재현 가능하고 테스트가 있다

### Phase 6. Home Credit 모델 비교 — 로지스틱 회귀(+ WoE 검토) vs XGBoost (4주)

- Phase 3과 동일한 비교 절차(층화 분할, CV, 하이퍼파라미터 탐색, AUC·상위 위험군 포착 성능)를 Home Credit에 적용
- 범주형·고결측 변수가 많은 만큼, 로지스틱 회귀 쪽은 WoE(Weight of Evidence) 구간화 적용 여부를 함께 검토
- **완료 기준**: 모델 파일, 성능 보고서, Home Credit 트랙 최종 모델 선정 근거 (GMC 대비 격차가 벌어졌는지 여부 명시)

### Phase 7. Home Credit 설명 체계 및 설명력 검증 (4주)

- Phase 6 결과에 따라 SHAP 또는 계수·WoE 기반 사유 코드 설계(Phase 4와 동일한 분기 원칙)
- 비선형 모델이 최종 채택된 경우, SHAP 설명이 스코어카드 수준의 설명력을 확보하는지 검증
  (예: 사유 코드의 일관성, 사례별 설명 타당성, `EXT_SOURCE_*` 등 블랙박스 변수가 상위 사유로 나올 때의 처리 방침)
- **완료 기준**: 대출자별 상위 N개 사유 코드 생성, 매핑 규칙 문서, 설명력 검증 결과(정성/정량)

### Phase 8. 두 데이터셋 비교 분석 (2주)

- GMC와 Home Credit 트랙 결과를 나란히 정리: 데이터 복잡도별 로지스틱-XGBoost 성능 격차, 설명 방식별 특성
- 서두의 연구 질문에 대한 답을 문서로 작성
- Phase 9(배치 파이프라인)에서 실제로 운영할 데이터셋/모델을 결정 (5절 미결정 사항 참고)
- **완료 기준**: 비교 분석 보고서(연구 질문에 대한 결론 포함), Phase 9 대상 데이터셋·모델 확정

### Phase 9. 스코어링·Spring Batch 파이프라인 (8주)

- Phase 8에서 결정된 데이터셋/모델을 대상으로 진행
- 모델 서빙 방식 결정 [미결정]
- 일일 재스코어링 Job: 청크 처리, 실패 재시도, 재실행 안전성
- 결과 저장: 대출자 ID, 기준일, 모델 버전, 점수, 사유 코드
- **완료 기준**: 배치 1회 실행으로 대상 전체 스코어링·저장, 동일 입력 재실행 시 동일 결과

### Phase 10. 배포·문서화 (5주)

- EC2 배포, nginx, CI/CD
- README: 문제 정의, 아키텍처, 설계 결정과 트레이드오프(두 데이터셋 비교 결과 포함), 데이터 한계, 실행 방법
- **완료 기준**: 외부 접속 가능한 데모, 면접 설명용 문서

### 여유·선택 확장 (약 4주)

데이터셋 확장(Phase 5~8)이 추가되면서 기존 계획 대비 여유가 10주 → 4주로 줄었다. 아래 제안 중 채택할 항목이 있다면
우선순위를 신중히 골라야 한다.

## 4. 제안 항목 (미확정)

| 제안 | 기대 효과 | 비용·고려사항 |
|---|---|---|
| 로지스틱 회귀 + WoE 스코어카드 기준 모델 | "왜 XGBoost인가"에 답할 근거, 금융권 표준과 비교 | 로지스틱 회귀를 베이스라인으로 비교한다는 원칙 자체는 3절 Phase 3·6으로 **확정됨**. 정식 WoE 구간화·스코어카드 구현 여부(특히 Home Credit)는 여전히 미확정 — Phase 6에서 검토 |
| 확률 보정 및 등급 매핑 | 점수를 연체 확률로 해석 가능 | 약 2주 |
| PSI 드리프트 모니터링 | 운영 설계 역량 시연 | 날짜가 없어 인위적 분포 변형 시나리오로만 시연 가능. PSI는 점검 트리거이며 성능 판단은 별도 지표로 해야 함 |
| 모델 버전 관리·챔피언–챌린저 | 모델 교체 절차 시연 | 배치·저장 구조 확장 필요 |
| Vue 대시보드 | 사유 코드·점수 조회 시각화 | 약 4~6주 |

## 5. 미결정 사항

1. **모델 서빙 방식**
   - A. Python 스코어링 서비스를 두고 Spring Batch가 호출: Python 생태계 그대로 사용, 서비스 하나 추가
   - B. XGBoost4J로 Java에서 직접 스코어링: 단일 런타임, 기여도 예측으로 SHAP 값 계산 가능, 전처리 로직을 Java로 재구현 필요
   - Phase 8에서 결정되는 최종 모델(로지스틱 vs XGBoost)에 따라 선택지가 달라질 수 있음(로지스틱이면 B가 훨씬 단순해짐)
2. **Phase 9 배치 파이프라인의 대상 데이터셋**: GMC(운영 단순성, 단일 테이블) vs Home Credit(주 데이터셋 일관성, 다중 테이블이라
   배치 설계가 더 복잡함) — Phase 8 비교 분석 이후 결정
3. **일일 배치 대상 시뮬레이션**: 데이터가 정적이므로 홀드아웃이나 테스트 데이터를 날짜별 묶음으로 나눠 투입할지 등
4. **`age` 사용 정책**: 모델 사용 여부, 사유 코드 노출 여부
5. **DB 종류**(MySQL / PostgreSQL)

## 6. 면접 대비 질문

- 이 데이터를 선택한 이유와 한계는? 왜 데이터셋을 두 개(GMC, Home Credit) 썼는가?
- 데이터 복잡도에 따라 XGBoost의 성능 이점이 어떻게 달라졌는가? 그 근거는?
- 결측과 이상값(96/98, 큰 DebtRatio)은 어떻게 처리했고 왜 그렇게 했나?
- SHAP 값을 사유 코드로 바꿀 때 상관된 변수는 어떻게 다뤘나?
- SHAP 기반 설명이 스코어카드 대비 실제로 얼마나 설명력이 있었나? (블랙박스 변수가 있는 Home Credit에서는?)
- 고객에게 보여주면 안 되는 사유는 어떻게 처리했나?
- 배치 재실행 시 결과 일관성은 어떻게 보장했나?
